# ComparePlans recommendations catalog

_Generated by `python ComparePlans_v1.py --dump-catalog`. Do not edit by hand -- edit the `RECOMMENDATIONS` dict in `ComparePlans_v1.py`. `test_compareplans.py` asserts this file is byte-identical to a fresh dump._

One row per signal or detection the tool can recommend on. A code that fires with no row here still appears under `SIGNALS`; it simply has no canned fix -- that is the `--emit-prompt` case.

| code | recommendation | standard fix | when it does not apply |
|---|---|---|---|
| `ACCESS_REGRESSED` | A table went seek -> scan and reads rose | Restore the index the better version used, or make the predicate sargable (no function / CONVERT on the filtered column). | A deliberate scan is correct when the query touches most of the table. |
| `BATCH_MODE_LOST` | Dropped from batch mode to row mode | Remove whatever disabled batch mode -- a DISALLOW_BATCH_MODE / USE HINT, or a construct that forces row mode. Confirm a columnstore index or the batch-mode-on-rowstore conditions still hold. | Row mode can win on a small result where batch-mode startup is not amortised. |
| `CE_MISS_WORSE` | Worse cardinality estimate driving the plan | Update statistics on the filtered columns. If a local variable or non-sargable predicate is involved, fix that. Run usp_TippingPointAnalysis for the exact estimate and the value where the plan flips. | A large ratio on a tiny operator (few rows either way) may not be material. |
| `COST_DOWN_READS_UP` | Lower estimated cost, more actual work -- rank on reads, not the cost % | Choose the version with fewer logical reads. If the cheap-looking plan is a seek + lookup, cover it; if it is a scan the optimizer under-costed, check statistics and the row estimate. | Cost is always an estimate; this is a reason to distrust it here, not a fix. |
| `EAGER_INDEX_SPOOL` | SQL Server is building a temporary index at run time | Create the permanent index the spool stands in for. The skeleton below is from the spool's own keys and output -- review against the existing indexes. | If the spool is over a small set at production scale it can be cheaper than maintaining another index. |
| `GRANT_GREW` | Memory grant doubled or more | The optimizer expects more rows through a memory-consuming operator. Update statistics; check for a new sort/hash the other version avoids. | A larger grant is fine if the version is faster and the memory is there. |
| `GRANT_OVERALLOCATED` | Grants far more memory than it uses | Remove a MIN_GRANT_PERCENT hint, add MAX_GRANT_PERCENT, or fix the over-estimate feeding the grant. Over-grant starves other queries under concurrency. | Ignore for a query that runs once in isolation. |
| `HASH_AGG_HIDES_GROUPING` | The GROUP BY is hashed, so index tools cannot see what it groups by | Nothing here is wrong with the query -- this is about getting a good index suggestion for it. In order: (1) build the index the missing-index suggestion proposes, if there is one, and re-capture the plan -- once the rows arrive in order the optimizer usually switches to a Stream Aggregate on its own, and the grouping becomes visible; (2) if the query is supposed to return sorted rows, add the ORDER BY it needs, which often produces that same shape; (3) LAST RESORT, and only to look -- compile it once with OPTION (ORDER GROUP) under SET SHOWPLAN_XML ON (nothing executes) and pass that plan to usp_IndexAnalysis @StatementPlanXml. That hint forces a Stream Aggregate, so the grouping columns become readable and you get the realigned index to build. | If you use the hint, take it back out again -- it is a way to SEE the index you need, not the fix. On its own it forces a sort that was not there and makes the query slower; once the index exists it changes nothing. And a hash aggregate is often the right choice, so this is a note about what the tooling can read, not a fault to correct. |
| `IDENTICAL_PLAN` | The rewrite compiled to the same plan | Do not ship this as a fix -- any runtime difference is data or parameter values. To get a different plan the change must alter the optimizer's options (an index, a hint, a sargable predicate). | None. |
| `IMPLICIT_CONVERSION` | An implicit type conversion is changing the plan | Align the parameter or literal type to the column's type so no CONVERT lands on the column side. | A conversion on the literal side (not the column) is harmless. |
| `LAZY_SPOOL_RECURSIVE` | A recursive CTE's own working table (Lazy Spool) | Not an indexing problem -- the spool is SQL Server's required bookkeeping for the recursion. If the tempdb cost matters, bound MAXRECURSION, or restructure the recursive member so it does not need to carry the full accumulated history (e.g. track only the latest level if that is all the query needs). | Present in essentially every recursive CTE; this is a note, not a defect. Its tempdb cost scales with recursion depth and fan-out, not with an absent index. |
| `LAZY_SPOOL_REWIND` | A repeatedly rewound branch is being cached instead of re-executed | Not an indexing problem -- an index does not remove the spool. Check whether the correlated, per-outer-row pattern driving the rewind can become a single set-based join instead. | SQL Server chose to cache because re-executing the branch per row was estimated as more expensive; removing the spool without removing the rewind can make the plan slower, not faster. |
| `LOCAL_VARIABLE` | <the variable> drives the estimate -- a fixed guess, not the histogram | Replace <the variable> with a parameter, add OPTION (RECOMPILE) to fold it to a compile-time literal, or make it a constant. Run usp_TippingPointAnalysis for the estimate it produces and the value where the plan tips. | OPTION (RECOMPILE) trades a compile per execution for accuracy -- fine for a low-frequency statement, not a hot one. |
| `LOOKUP_EXPLOSION` | Key/RID lookups are the cost -- cover the query or stop reusing a selective plan | Add a covering index so the lookup's columns are in the index, or -- if this is one plan compiled for a rare value and reused for common ones -- fix the reuse with OPTIMIZE FOR / OPTION (RECOMPILE) / (2022+) parameter-sensitive plans. | If the lookup count is small at production scale, or the index already covers and the plan just chose wrong, an index will not help. |
| `NEW_LAZY_SPOOL_RECURSIVE` | This version's query is recursive where the baseline's is not (or recurses less) | Not necessarily a defect to fix -- confirm whether the recursion is intentional and correct (the baseline may simply not handle the same cases). If the tempdb cost matters, bound MAXRECURSION or restructure the recursive member. | A recursive CTE's own working table is required bookkeeping, not something an index removes -- do not chase this the way a genuine regression is chased. |
| `NEW_LAZY_SPOOL_REWIND` | New Lazy Spool caching a rewound branch that the baseline does not need | Not an indexing problem. Check what changed about the query shape -- a rewrite that introduced a correlated per-row pattern, or a plan choice a fresher statistics update would revert -- rather than adding an index. | A spool is deliberate caching machinery, not a tempdb spill -- do not conflate this with NEW_SPILL/SPILL_GREW, which are a memory-grant overflow warning on a Sort/Hash, an unrelated concept. |
| `NEW_SPILL` | New spill to tempdb | Fix the row estimate the sort/hash is sized from (update statistics, remove a local variable), raise the memory grant, or add an index that removes the sort. | A one-level spill on a large sort at production scale is not always worth chasing. |
| `NON_SARGABLE_PREDICATE` | A function / CONVERT on the filtered column blocks an index seek | Compare on the column's native type: move the CONVERT/expression to the other side of the comparison, or persist the derived value in a computed column and index it. | If the column genuinely needs transforming per row, a computed column + index is the route, not a rewrite. |
| `NO_JOIN_PREDICATE` | A join has no ON condition | Add the missing join predicate -- an unintended cross join multiplies row counts. | Frequently benign for a deliberate 1-row cross join; confirm it is intended. |
| `NO_STATISTICS` | The optimizer had no statistics on a filtered column | CREATE STATISTICS on the named column(s), or confirm AUTO_CREATE_STATISTICS is ON for the database. | None. |
| `QUERY_HASH_MISMATCH` | The versions are not the same query text | Confirm they return the same result set before choosing between them -- this tool does not check semantic equivalence. | Expected when comparing genuine rewrites; still verify the results. |
| `ROW_GOAL` | A row goal (TOP / FAST N / EXISTS) is shaping the plan | Compare the versions like-for-like -- a row goal makes the plan stop early, so reads and the seek/scan choice are not comparable to a version without one. If the row goal is unintended, remove the TOP / FAST hint. | Usually intended; this is a note, not a defect. |
| `SPILL_GREW` | Both versions spill; this one moves far more tempdb | Same as a new spill -- estimate, grant, or index. Check granted-vs-used memory in RESOURCE DELTAS first; if a grant hint caused it, back the hint off. | None beyond the grant-hint case. |
| `TABLE_VARIABLE_1ROW` | <the variable>: a table variable estimated at 1 row, feeding a join | Switch <the variable> to a #temp table (it gets statistics and a real estimate), or add OPTION (RECOMPILE) so the count is known at compile time. On 2019+/compat 150 confirm table-variable deferred compilation is on. | A table variable that really holds ~1 row is fine. |
| `THREAD_SKEW` | Parallel workers are badly unbalanced | The distribution key sends most rows to one worker. Repartition on a more even key, or reconsider whether this query should run parallel. | Advisory -- no fixture reproduces this reliably; check the per-thread rows in the plan. |
| `UDF_DOMINATES` | A scalar UDF is most of the elapsed time | Inline the scalar UDF (SQL Server 2019+ does this automatically when it qualifies), or rewrite it as an inline table-valued function or a computed column. | None -- a per-row scalar UDF over a large set is almost always the whole cost. |
| `UDF_TIME_UP` | Scalar-UDF time went up | Same as UDF_DOMINATES -- inline it or convert to an inline TVF. | A small absolute change on a small set may not matter. |
